# 方剂数据导入与向量化操作手册

> 针对 `fangji.sql`（方剂 24870 + 中药材 11242 + 偏方 1593，共 37705 条）的完整入库流程。
> 所有路径基于本机项目根目录 `F:\workspace\zhongyishizhan`。

## 一、整体链路

```
fangji.sql
  │  ① mysql 导入
  ▼
MySQL 的 fangji 库（fangji / zhongyao / pianfang 三张源表，只读保留）
  │  ② clean.py 清洗（去 HTML → "标签：内容"分段）
  ▼
MySQL 的 tcm.knowledge 表（review_status=1, vector_status=0）
  │  ③ embedding.py 向量化（bge-large-zh CPU 编码 → Chroma）
  ▼
Chroma 向量库 tcm_knowledge 集合 + knowledge.vector_status=1
  │  ④ 重启服务（重建 BM25 缓存）
  ▼
问答接口可用
```

项目原生就为这套数据设计：`knowledge.source` 字段取值就是 `fangji / zhongyao / pianfang`，
`com/tcm/etl/clean.py` 的 `SOURCES` 常量直接指向 `fangji.fangji` 等三张表。

## 三、首次导入（已完成，供重跑参考）

### 2. 清洗入库到 tcm.knowledge

```bash
# 先小批量验证（每表 100 条），确认清洗规则匹配
".venv\Scripts\python.exe" -m com.tcm.etl.clean --limit 100

# 全量（幂等：knowledge 上 (source,src_fid) 唯一键，重跑不插重）

```

实测结果：输入 37705 → 入库 37654（过滤 51 条空内容）。
清洗把 HTML `<p class="drug ..."><span class="fieldname">处方</span>...</p>`
转成 `处方：阿魏15克...` 这样的纯文本行，供后续按行切块。
导入后这些记录 `review_status=1`（已复核）、`vector_status=0`（待向量化）。

### 3. 向量化

**当前使用模型：bge-small-zh-v1.5**（配置在 `.env` 的 `EMBED_MODEL_PATH`，512 维）。
它是 bge-large 的轻量版，实测编码真实医案约 5 条/秒，比 large（0.1 条/秒）快约 50 倍，
中医科普/方剂检索场景精度足够。若追求最高精度可改回 large，但全量要跑十几小时。

**最推荐：自动分批脚本 `scripts/run_batches.sh`**（解决长跑段错误，无需值守）：

```bash
# 在 Git Bash 里执行（每批 2500 条，全新进程，跑完自动续下一批直到全部完成）
bash scripts/run_batches.sh

# 进度看日志
tail -f .embed_batches.log
```

为什么用它：bge-large 长跑会内存累积导致 Segmentation fault（实测跑 4-5 小时后崩溃）。
分批脚本每批用全新 Python 进程（彻底释放内存），单批 2500 条约 2 小时，在崩溃临界点前收工；
某批若异常退出会自动等 5 分钟重试同批。断点续跑，数据不丢。

**单批手动跑用优化版 `scripts/fast_embed.py`**（大批次 upsert，比原版快近 1 倍）：

```bash
# 全量：处理所有 review_status=1 且 vector_status=0 的记录（推荐）
".venv\Scripts\python.exe" "scripts/fast_embed.py" --limit 0

# 或先小批量试跑（如 500 条）
".venv\Scripts\python.exe" "scripts/fast_embed.py" --limit 500

# 内存充足时可加大 flush 阈值减少 upsert 次数
".venv\Scripts\python.exe" "scripts/fast_embed.py" --limit 0 --flush-seg 1024
```

原版脚本（每 64 段 upsert 一次，海量数据下很慢，仅作备用）：
```bash
".venv\Scripts\python.exe" -m com.tcm.rag.embedding --limit 0
```

关键机制：
- **按行切块**：一条知识的每个"标签：内容"行是一个 chunk，文本格式为 `标题｜标签：内容`
- **批量编码**：攒够 64 段一次性送 bge-large-zh（CPU）编码（实测 batch 64/128/256 吞吐一致）
- **大批次写入**：优化版攒够 512 段才 upsert 一次并批量回写状态，减少 HNSW 索引反复重建
- **断点续跑**：只处理 `vector_status=0` 的记录，写完一批就回写 1；中途中断/崩溃，重跑自动接着来，已完成的不重算
- **进度输出**：每 50 条打印速度/预计剩余时间

**速度与耗时（本机 AMD Ryzen 9 7940H / 8 核，实测）**：
- 编码吞吐约 5.5 段/秒（真实文本），每条约 6 段 → 约 0.9 条/秒
- 3.7 万条全量预计 **8-12 小时**，属正常，适合夜间后台跑
- 内存占用约 2.4GB；**建议跑向量化时先停掉 uvicorn 服务**，避免两个进程各加载 1.4GB 模型导致内存不足段错误（Segmentation fault）

**数据安全**：向量库在 `F:\workspace\zhongyishizhan\chroma_db`（F 盘），
MySQL 数据也在 F 盘，中断不会丢数据，重跑续上即可。

### 4. 重启服务（必须）

```bash
".venv\Scripts\python.exe" -m uvicorn com.tcm.main:app --host 127.0.0.1 --port 8000
```

**为什么必须重启**：服务常驻进程内的 Chroma 客户端和 BM25 缓存持有旧状态，
不重启会出现 `hnsw segment reader: Nothing found on disk` 或检索不到新数据。

## 四、日常增量操作

### 场景 A：又拿到一批新 SQL

重复第三节 1→2→3→4。clean.py 和 embedding.py 都是幂等/增量的：
- clean.py 用 `(source, src_fid)` 唯一键，已存在的会更新内容而非重复插入
- embedding.py 只挑 `vector_status=0` 的，已入库的不重算

### 场景 B：只想重算某一条知识的向量

```bash
".venv\Scripts\python.exe" -m com.tcm.rag.embedding --one 123
# 123 = knowledge.id
```

会先删掉该条旧 chunk 再重新切片写入，并让 BM25 缓存失效。

### 场景 C：管理端编辑了一条知识后

后台编辑接口已自动调用 `revector_one()`，无需手动操作。

### 场景 D：清空/重建向量库

1. 停服务
2. 删除 `chroma_db` 目录
3. 把所有 `knowledge.vector_status` 重置为 0：
   ```sql
   UPDATE knowledge SET vector_status = 0;
   ```
4. 重新执行第三节 3、4 步

## 六、常见问题

- **问答报 `division by zero`**：已修复（`bm25.py` 空 corpus 短路）；若仍出现，确认 knowledge 表有 `vector_status=1` 的数据。
- **检索不到新数据 / hnsw 错误**：八成是向量化后没重启服务，重启即可。
- **导入 SQL 报乱码**：确认 mysql 命令带了 `--default-character-set=utf8mb4`。
- **向量化很慢**：正常，CPU 编码 20 万段耗时较长；支持随时中断续跑。
- **portal 8000 端口冲突**：先停掉旧 uvicorn 进程再启动。
